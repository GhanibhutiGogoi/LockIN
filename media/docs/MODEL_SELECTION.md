# Quality-first model selection — 15 November 2026

Decision for LockIn: **LTX-2.5 with the official DFR quality pipeline** for
offline gameplay and b-roll; **Fish Audio Drama 3** for directed narration;
**Qwen3-ForcedAligner-0.6B** as an auxiliary timing model. These are researched
candidates, not winners of our own bake-off. No capable GPU was available for
this implementation. The revised hardware budget is **128 GB total across
multiple GPUs**, not one 128 GB accelerator.

## What “best” means here

The important voice properties are understandable technical terms, lively
delivery, stable speaker identity and fidelity to the lesson. For video they
are coherent repetitive motion, clean central framing and tolerable loop
seams. A general preference leaderboard does not directly measure any of our
learning outcomes. Choose a strong quality candidate now, then test the actual
prompts on the eventual GPUs before accepting output into a study.

The earlier low-memory Wan/Kokoro shortlist is superseded by the user's
quality-first requirement. More VRAM lets us consider larger models; it does
not itself establish quality or make the latest runtime run on an older card.

## Licensing correction and product boundaries

The proposal's blanket exclusion of Drama 3 was too broad. Its actual
[community license, §III(c)](https://huggingface.co/fishaudio/drama-3/blob/main/LICENSE)
explicitly excludes speech for content generated by one's own product from
the restricted “Hosted Service” category. Its community commercial grant has
a USD 500,000 annual-revenue threshold and other conditions. A generic TTS or
voice-cloning API is a different use. This implementation keeps the raw model
servers private and integrates narration into LockIn; review the complete
terms for the eventual deployment and retain required notices.

LTX-2.5 weights have a custom community license and gated downloads; its code
license is a separate matter. The download command requires the operator's
existing Hugging Face access and does not accept terms on their behalf. The
library metadata labels published videos as AI-generated. The web UI still
needs a suitable user-facing AI-generation disclosure before release.

## Why a third, small model is included

Drama 3's self-hosted reference API returns audio. We do not assume it has the
same word-timing features as a hosted commercial API. Caption timing uses
[Qwen3-ForcedAligner-0.6B](https://huggingface.co/Qwen/Qwen3-ForcedAligner-0.6B),
aligning the known script to the paced narration. Its
[documented API](https://github.com/QwenLM/Qwen3-ASR#forcedaligner-usage)
returns text with start/end times. It has Apache-2.0 weights.

The service preserves punctuation and the UI's whitespace token count instead
of trusting the aligner's tokenization. It rejects mismatches and impossible
times rather than inventing uniform timestamps in real mode. Forced alignment
does **not** prove that the TTS pronounced every word correctly; listening and
independent transcription checks remain part of evaluation.

## 128 GB across several GPUs: actual deployment implications

The example topology is four 32 GB NVIDIA cards. The exact card models and
interconnect are still unknown. The implementation makes two separate choices:

* **Drama 3:** the official reference runtime documents a comma-separated
  device list, with the audio tower/codec on its final device. We expose that
  list rather than guessing a `tensor_parallel_size` flag. Official single-card
  guidance is at least 48 GB in its FP8 path. The reference implementation has
  an older-GPU fallback, but upstream explicitly calls the V100 path untested.
  [Installation](https://speech.fish.audio/install/),
  [inference/device list](https://speech.fish.audio/inference/).
* **LTX-2.5:** its official sequence-parallel multi-GPU mode keeps a complete
  working transformer replica on every GPU. It is a latency tool, not memory
  pooling. Our initial profile uses `--offload cpu` on one selected card,
  streaming BF16 layers while keeping weights in host RAM. This trades speed
  for a lower device footprint without adding weight quantization.
  [Multi-GPU documentation](https://github.com/Lightricks/LTX-2/blob/main/packages/ltx-pipelines/docs/multigpu/README.md),
  [offloading documentation](https://github.com/Lightricks/LTX-2/blob/main/packages/ltx-pipelines/docs/optimization.md).

Generate the video library offline, release the video process, then start
voice serving on the same cards. Do not assume both large models fit
concurrently merely because their combined nominal weights are below 128 GB.
We recommend planning for 256 GB system RAM and 300 GB free disk; these are
capacity allowances, not measured minima. The CPU aligner preserves GPU headroom.

The pinned LTX runtime currently resolves CUDA 13.2 / PyTorch 2.13 for its
NATTEN path. The Fish environment uses its supported CUDA 12.6 profile.
Drivers must support both. If the cards are Tesla V100s, do **not** assume the
LTX configuration works: the current CUDA/NATTEN path needs a hardware-specific
reassessment. VRAM capacity does not imply BF16, FP8 or kernel support.

No memory fit, clip throughput, cold-start latency or narration real-time
factor has been measured. The 60-second UI request deadline is addressed by
prewarming and durable caches, not by claiming that a model will meet it.

## Prompt and output decisions

* Video: one subject/action, fixed camera language, original art direction,
  central crop-safe composition. Default 1280×1024 (5:4) matches the lower
  player panel more efficiently than a full portrait canvas. 121 frames at
  24 fps is a starting experiment, not a validated optimum.
* DFR: use the official distilled transformer, matching fine-tuned text encoder,
  diffusion video VAE, audio VAE and spatial-detail LoRA. Do not mix 2.3/2.5
  components or substitute a stock text encoder. The native DFR interface
  does not consume a negative prompt; constraints are in the positive prompt.
* Voice: store an original synthetic reference for each narrator. Apply one
  brief delivery direction; leave the lesson's words unchanged. Pronounce
  formulas as speech upstream. Avoid laughter tags until alignment and
  pronunciation are evaluated; they add sound absent from caption text.
* Pacing: time-stretch before alignment. The actual duration is reported.
  Long scripts are not truncated to satisfy `target_seconds`.
* Loop processing: forward-only tail/head crossfade; no reverse playback.
  Outputs require visual review before entering the gameplay library.

## First hardware evaluation

Use the same fixed scripts and seeds across candidates. Keep short snippets
covering plain science, slang, acronyms, numbers and a 60-second explanation.
Measure peak VRAM **per GPU**, host RAM, startup time, wall time, audio duration,
word omissions, pronunciation, identity consistency and caption offset. For
video, generate several seeds for each of the four presets and watch repeated
loops for object deformation, flicker, camera jumps and seam artifacts.

A sensible initial acceptance bar is: no changed/omitted lesson facts, no
unintelligible key terms, monotonically valid captions with no obvious drift,
stable narrator identity, and reviewed loops with no jarring cuts. Timing and
quality thresholds should be recorded from actual tests; do not claim the
proposal's two-second rescue target for uncached neural inference.

The repo tests use synthetic media and mock model servers. They exercise our
software contract; they are not evidence of either selected model's quality.
